# x402 verification purchases

Two independent transfers exist: the requester agent pays the verifier through x402/Blocky402; the marketplace operator pays the task reward to the collaborator's account snapshotted at claim time. Both use Hedera testnet HBAR. Account IDs are numeric `0.0.x`, not EVM addresses. An approved mock decision can release real testnet HBAR; a rejected/manual-review decision still consumes the purchased analysis and has no reward. Automatic refunds are not implemented.

## Configuration

In the server `.env`, set `VERIFICATION_PAYMENT_MODE=x402`, `BLOCKY402_BASE_URL=https://api.testnet.blocky402.com`, `X402_VERIFIER_PRICE_HBAR=0.001`, `X402_PAY_TO_ACCOUNT_ID=<verifier account>` and `API_BASE_URL=<client-reachable API origin>`. Use HTTPS outside local development. The facilitator fee-payer account is discovered from `/supported`, never hardcoded. The verifier recipient must differ from that fee payer.

Keep the agent's funded account separate from the operator and verifier. Copy `.env.agent.example` to `.env.agent`, then put `AGENT_HEDERA_ACCOUNT_ID=0.0.x` and `AGENT_HEDERA_PRIVATE_KEY=<DER private key>` there. The host CLI loads this file after `.env` and intentionally overrides same-named placeholders. The owning agent's API token, API base URL and expected verifier recipient can remain in `.env` or be overridden in `.env.agent`. Server containers do not receive agent payment keys. Never commit or paste these credentials.

The example environment opts into x402. Omitting the setting defaults to `free_mock` for compatibility. Each new task commits its payment mode into its canonical specification. Migration 003 backfills existing tasks as `free_mock` without changing historical specifications, hashes or HCS records. Changing configuration does not convert existing tasks. The configured fixed price must be within the task's `verificationPriceLimit`; both server and client enforce this in integer tinybars.

## Purchase protocol

1. Submit evidence and wait for `EvidenceSubmitted` HCS confirmation. Paid tasks remain `EVIDENCE_SUBMITTED`; they cannot run analysis yet.
2. The owning agent posts `{"taskId":"<uuid>"}` to `/v1/x402/verify` with its bearer token and persistent `Idempotency-Key`.
3. The API checks retained evidence and budget, persists one quote and returns HTTP 402 with the base64 JSON `PAYMENT-REQUIRED` header. It uses x402 v2, scheme `exact`, network `hedera:testnet`, asset `0.0.0` (HBAR), integer tinybars, verifier recipient and a dynamically discovered `extra.feePayer`.
4. The CLI validates origin, recipient, network and budget, signs one transfer and durably saves the authorization before sending it as `PAYMENT-SIGNATURE` with the same body/key. `extra.memo=fieldproof:x402:<purchase UUID>` must be included in the signed transaction. Use the provided signer in `src/x402-client.ts`; a generic signer that ignores this memo extension is not compatible.
5. The API checks binding and facilitator `/verify`, persists the authorization and queues settlement before returning 202. This means accepted for processing, not paid. A quote alone is not authorization to settle.
6. The worker calls facilitator `/settle` with the same v2 authorization and requirements. Confirmation, transition to `VERIFYING` and the analysis job commit atomically. An ambiguous response is reconciled against Mirror Node before retrying the same transaction. It never creates a replacement signature.
7. Poll `/v1/x402/payments/<id>` and then `/v1/tasks/<taskId>/result`. Replaying the purchase endpoint after confirmation includes `PAYMENT-RESPONSE`; a completed analysis returns 200. `VerificationCompleted` HCS v2 binds the actual payment-reference hash. Receipt verification independently checks the transfer and HCS binding.

No legacy `X-PAYMENT` headers are used. A 402 is not stored as an immutable generic idempotency response: the same key advances the same purchase from quote to authorization. New keys cannot create a second purchase for the same task. Altering an accepted authorization or reusing its transaction ID elsewhere is rejected.

## CLI and recovery

```bash
npm run x402:preflight
npm run x402:buy -- <taskId>
```

Run preflight after the API is ready and principals have been seeded. It performs read-only checks against Blocky402, Mirror Node and the local API: supported x402 v2 Hedera mode, account existence and balances, operator/agent public-key matches, topic existence and token roles. It reports only public account IDs, balances and status; it never prints keys or tokens. The demo expects four distinct accounts and checks at least the configured fee reserve plus 0.1 HBAR on the operator and the verification price on the agent.

The demo invokes the same client after the evidence HCS event. The CLI uses an exclusive per-task journal under `.x402-payments` (or `X402_JOURNAL_DIR`), with directory mode 0700 and new file mode 0600. Protect its parent directory and backups. It saves signed bytes before submission and reuses them after a lost response. If the API already has authorization, the CLI resumes polling without signing again. Polling times out after four minutes without cancelling the purchase; rerun the same command to recover.

An incomplete journal fails closed. Do not remove it to force a retry. Quotes expire after five minutes and signed transactions have a 120-second duration; an expired signed transaction is never automatically replaced. Unknown settlement is not proof of failure. Inspect the existing transaction on Mirror Node, purchase status and the operator job queue before intervention. Retry a blocked job only to reconcile or resend the same authorization. Replacement purchases/refunds require a separately designed operator workflow and are not implemented.

Persisted statuses are `QUOTED`, `AUTHORIZED`, `SETTLING`, `CONFIRMED`, `UNKNOWN`, `FAILED`. Unknown/blocked payments do not unlock analysis or rewards. Authorized purchases pin evidence until analysis completes or payment conclusively fails; monitor these states to avoid indefinite retention.

## Validation boundary

Automated tests use actual SDK signatures, PostgreSQL and MinIO, with fake facilitator/ledger settlement. They cover purchase gating, budgets, ownership, replay protection, concurrency, ambiguous settlement recovery and reward separation without spending funds. A real paid end-to-end run still requires funded testnet credentials. Acceptance requires the actual x402 transfer, HCS v2 payment hash, collaborator reward at the claimed account and successful Mirror Node receipt checks. Mock image analysis remains an explicit limitation even after all financial checks pass.
