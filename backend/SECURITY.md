# Security and limitations

- Testnet is enforced by configuration and the Hedera client. No collaborator private key is accepted or stored.
- Demo principals use distinct opaque tokens hashed with SHA-256 in PostgreSQL. `GET /v1/me` provides the caller ID; authorization checks agent ownership and worker claims. There is no public registration, password flow or wallet custody.
- Rotate/revoke demo access by updating/removing the relevant token hash under operator control. Running seed with a different token does not revoke old credentials. Treat DB access as administrative access.
- Signed upload URLs expire in five minutes. Clients receive no private destination keys or permanent download URLs. MIME detection, full JPEG decode, dimensions, metadata, declared byte count and SHA-256 are validated before submission. HTTPS proxy limits uploads to 10 MiB. Direct local S3 is a development interface.
- The evidence copy uses server-validated bytes and client-inaccessible keys. A later overwrite of a staging URL cannot change committed evidence. Exact duplicate detection persists across the seven-day image retention period; it does not detect visual edits or prove liveness.
- Mandatory idempotency keys bind caller, route, resource and request body. Payload changes under the same key return 409. Database constraints prevent two claims or reward operations for one task. Completed idempotency responses are retained for the demo lifetime.
- HCS strict schemas reject unknown fields. Legacy/free events use v1 without payment references; paid verification uses v2 with the hash of the confirmed transaction reference. Recipient account IDs appear in actual network transfers, not HCS messages.
- Agent payment keys belong only in the CLI environment (`.env.agent`), never in API requests or server configuration. Compose clears agent key/account variables for API, worker and migration containers. The collaborator supplies an account ID, never a private key.
- x402 authorization is validated against immutable requirements, purchase memo, evidence and the agent's budget. The facilitator verifies signatures; the worker settles only persisted authorizations. The database and the CLI journal contain replayable signed authorizations: protect both and do not log `PAYMENT-SIGNATURE` headers. Never delete a journal just to retry a payment.
- Default rate limiting is 100 requests/minute/IP/process. Reverse-proxy deployment uses conservative shared proxy limits because forwarded headers are not trusted automatically. This is a small demo deployment, not distributed abuse prevention.
- API logs redact auth headers and do not log bodies or SDK errors. The database holds replayable signed transactions: protect database volumes and backups alongside the operator key.
- An uncertain or conclusively failed transfer is never replaced with a new transaction automatically. Blocked jobs expose safe error codes and require investigation. Reconciliation depends on availability/retention of SDK receipts and Mirror Node; absence is not proof of failure.
- `APPROVED` from the mock can pay real testnet HBAR. Do not represent it as actual visual verification. The QR identifies an asset; it does not prove location, identity or authenticity.

Dependencies are pinned in `package-lock.json`. The backend and x402 use the same `@hiero-ledger/sdk` version. gRPC/protobuf/WebSocket transitive overrides retain patched compatible major versions. React Native peer packages are omitted because this is a Node server. Re-run unit tests, SDK serialization checks and `npm audit` when updating dependencies; a clean audit is not a substitute for security review before broader use.
